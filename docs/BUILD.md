# Сборка Vantara

Два режима: быстрый прототип интерфейса и полная сборка форка.

---

## Режим 1 — Прототип интерфейса

Ничего компилировать не нужно. Цикл правки — секунды.

### Требования

- Firefox Developer Edition (или Nightly / обычный Firefox)
- PowerShell

### Запуск

```powershell
.\tools\dev-profile.ps1
```

Скрипт создаст профиль в `.dev-profile`, подключит к нему `ui/chrome` через
junction и запустит браузер.

Если Firefox не установлен, скрипт скачает portable-сборку в `.dev-runtime`,
не трогая систему:

```powershell
.\tools\dev-profile.ps1 -Fetch
```

### Работа

| Действие | Как |
|---|---|
| Применить правки CSS | `Ctrl+Alt+R` в окне браузера |
| Отладчик интерфейса | `Ctrl+Alt+Shift+I` (Browser Toolbox) |
| Чистый профиль | `.\tools\dev-profile.ps1 -Reset` |

В Browser Toolbox доступен инспектор по интерфейсу браузера так же, как по
обычной странице: можно найти нужный селектор и проверить правило на месте.

### Проверка интерфейса

Скриншот показывает результат, но не объясняет причину: правило не сработало
из-за опечатки, из-за незагруженного файла или потому что Firefox перекрыл
его своим. Два инструмента отвечают на это точно, читая живое окно браузера
через Marionette — штатный протокол автоматизации Mozilla.

Браузер для этого запускается в режиме инспекции:

```powershell
.\tools\dev-profile.ps1 -Inspect
```

| Команда | Что отвечает |
|---|---|
| `python tools/inspect-ui.py` | Дошли ли токены, какие правила выиграли у Firefox |
| `python tools/audit-selectors.py` | Есть ли селекторы, которые ни к чему не относятся |
| `.\tools\screenshot.ps1` | Снимок окна в `docs/screenshots/` |

**Запускать после каждого обновления движка.** Firefox меняет разметку chrome
между версиями, и устаревший селектор не даёт никакой ошибки — правило просто
молча перестаёт работать. Так в Firefox 157 фон адресной строки переехал
с `#urlbar-background` на `.urlbar-background`, и половина интерфейса осталась
стандартной при полностью «рабочем» на вид CSS.

### Тесты

```bash
node tools/test-url-parse.mjs
```

Проверяет разбор ввода адресной строки: что уходит в поисковую систему,
а что открывается напрямую. Ошибка здесь означает утечку — внутренний хост
вроде `router.local` или `intranet.company.ru` ушёл бы в поисковик вместе
с путём. Набор случаев только растёт, удалять из него нельзя.

## Режим 2 — Сборка форка

> Этап 3 роадмапа. Раздел описывает целевой процесс; окружение ещё не разворачивалось.

### Требования

| Что | Зачем | Объём |
|---|---|---|
| MozillaBuild | Оболочка сборки Mozilla под Windows | ~500 МБ |
| Visual Studio 2022 + C++ workload, Windows SDK | Компилятор | ~10 ГБ |
| Rust (stable, MSVC target) | Часть Gecko на Rust | ~2 ГБ |
| Node.js 18+ | surfer и сборочные скрипты | — |
| Git, Python 3.9+ | Инструменты Mozilla | — |
| **Свободное место** | Исходники + объектные файлы | **~60 ГБ** |

На этой машине уже есть: Node 22, Python 3.12, Rust 1.98, Git, VS 2022.
Не хватает **MozillaBuild** — https://ftp.mozilla.org/pub/mozilla/libraries/win32/MozillaBuild-Latest.exe

### Порядок

```bash
# 1. Инструмент сборки форков (написан командой Zen Browser)
npm install -g @zen-browser/surfer

# 2. Инициализация проекта: версия Firefox, имя приложения, бренд
surfer init

# 3. Скачать исходники Firefox в engine/ (~30 ГБ, долго)
surfer download

# 4. Наложить наш оверлей src/ и патчи на исходники
surfer import

# 5. Сборка. Первый раз — 1-3 часа, дальше инкрементально
surfer build

# 6. Установщик
surfer package
```

### Обновление до новой версии Firefox

```bash
surfer update <версия>   # поднять версию движка
surfer import            # заново наложить наши изменения
```

Конфликты патчей вылезут на шаге `import` — их видно сразу, а не после сборки.
Для браузера с упором на защиту данных отставание от Firefox по патчам
безопасности недопустимо, поэтому обновление — регулярная операция, а не разовая.

### Как интерфейс попадает в собранный браузер

В прототипе стили подключаются через профиль (`userChrome.css`). В сборке
так нельзя: файл профиля пользователь может удалить, а интерфейс должен быть
частью продукта. Механизм другой — три шага, выверенные по исходникам.

**1. Файлы кладутся в тему.** `ui/chrome/vantara/*.css` →
`src/browser/themes/shared/vantara/`.

**2. Регистрируются в упаковке.** В `browser/themes/shared/jar.inc.mn`
каждая строка отображает файл исходника в адрес `chrome://`:

```
skin/classic/browser/vantara/tokens.css   (../shared/vantara/tokens.css)
```

Без этой строки файл просто не попадёт в сборку — и без единой ошибки.

**3. Подключаются к теме платформы.** В `browser/themes/windows/browser.css`
уже есть импорты вида `@import url("chrome://browser/skin/browser-shared.css")`.
Наш добавляется туда же. Для Linux и macOS — свои файлы `browser.css`,
и правку придётся повторить в каждом.

Порядок важен так же, как в прототипе: `@import` идёт раньше любых правил.

**Настройки** переносятся отдельно: `ui/prefs/user.js` →
`src/browser/app/profile/vantara.js`. Там они становятся заводскими
значениями — пользователь по-прежнему может их изменить, но в новом профиле
они уже применены.

### Что попадает в сборку

| Из репозитория | Куда в Firefox |
|---|---|
| `ui/chrome/vantara/*.css` | `src/browser/themes/vantara/` |
| `ui/prefs/user.js` | `src/browser/app/profile/vantara.js` (заводские дефолты) |
| `ui/pages/newtab/` | `src/browser/components/newtab/vantara/` |
| `brand/icons/` | `src/browser/branding/vantara/` |
| chrome-скрипты этапа 2 | `src/browser/base/content/vantara/` |

### Что пришлось чинить под Windows

Документация surfer написана под Linux и macOS. На Windows сборка упирается
в шесть препятствий подряд — ни одно из них не описано, и каждое выглядит
как «ничего не работает».

**1. Surfer ставится локально, не глобально.** При глобальной установке он
строит пути к своим шаблонам относительно рабочего каталога и теряет букву
диска: проект на `D:`, пакет на `C:` — и `import` падает на несуществующем
`D:\Users\...`. Поэтому `npm install --save-dev` и запуск через `npx`.

**2. `surfer build` не работает.** Он вызывает `./mach` напрямую, как в Linux.
На Windows это Python-скрипт без расширения, и cmd его не запускает. Сборка
идёт через обёртку `tools/mach.ps1`, поднимающую окружение MozillaBuild.

**3. `bash -l` теряет окружение.** Прямой вызов минует `msys2_shell.cmd`,
который обычно собирает `PATH`. Без этого mach падает на
`/usr/bin/env: python3: No such file`, а следом — на
`Could not determine home directory`: домашний каталог он вычисляет всегда,
даже когда `MOZBUILD_STATE_PATH` задан явно. Обёртка передаёт и `PATH`,
и `USERPROFILE`.

**4. Устаревший target в шаблоне.** Шаблон surfer задаёт
`x86_64-pc-mingw32` — Firefox 156 такой цели уже не принимает. Нужен
`x86_64-pc-windows-msvc`, основной тулчейн Mozilla под Windows.

**5. Бренд нужно назначить отдельно.** Без `npx surfer config brand stable`
сборка молча берёт `unofficial`, и получается Firefox без нашего брендинга.
Проверяется по строке `--with-branding` в `engine/mozconfig`.

**6. PowerShell съедает вывод ошибок.** Вывод native-команд в stderr версия
5.1 превращает в `NativeCommandError`, и настоящая ошибка теряется. Отладка
сборки — только через bash.

**7. Движку нужен свой git-репозиторий.** На двадцать второй минуте сборка
падает так:

```
git log -1 --format=%ad --date=iso engine/config/milestone.txt
  → exit status 128
mozmake: *** [fake.dll.rc] Error 1
```

Firefox берёт дату последнего изменения `config/milestone.txt`, чтобы
построить номер версии для ресурсов DLL. Он находит наш репозиторий —
`engine/` лежит внутри него — и спрашивает про файл, который перечислен
в `.gitignore`. Git отвечает ошибкой.

В коде предусмотрен случай «системы контроля версий нет вообще», но не
случай «git есть, а файл ему неизвестен». Лечится минимальным репозиторием
внутри движка, без патча:

```bash
cd engine
git init
git add -f config/milestone.txt
git commit -m "Milestone marker for build versioning"
```

Один файл в коммите, 3,4 ГБ исходников остаются неотслеженными. Каталог
`engine/.git` наружу не попадает: сам `engine/` игнорируется.

Повторять после каждого `surfer download`, который создаёт движок заново.

Отдельно: mach определяет запуск из-под ИИ-агента по переменной `CLAUDECODE`
и сокращает вывод до предупреждений и ошибок. Полный вывод — флаг `--verbose`.

### Типичные грабли

- **Сборка падает на нехватке места** — объектные файлы занимают больше самих
  исходников. Держать 60 ГБ свободными.
- **Антивирус тормозит сборку в разы** — исключить `engine/` и `obj-*` из
  проверки в реальном времени.
- **Долгий путь к файлам** — Windows и глубокая вложенность Gecko конфликтуют.
  Собирать близко к корню диска.
- **Изменения в `src/` не видны** — забыт `surfer import` перед `build`.
