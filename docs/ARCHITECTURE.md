# Архитектура Vantara

## Главное техническое ограничение

Сделать десктопный браузер на Gecko можно **только форком Firefox**. Это не выбор
из удобства, а единственный поддерживаемый путь:

- **XULRunner** (среда для сторонних приложений на Gecko) удалён Mozilla в 2015 году.
- **Embedding API** (встраивание Gecko в чужое приложение, как CEF для Chromium)
  Mozilla не поддерживает с тех же пор. Аналога CEF у Gecko нет.
- **GeckoView** — живой и поддерживаемый, но это Android-библиотека. Для Windows
  и Linux её нет.

Поэтому Vantara — форк исходников Firefox, в котором мы заменяем интерфейс,
настройки по умолчанию и часть поведения движка. Тем же путём идут LibreWolf,
Waterfox, Floorp, Zen Browser и Mullvad Browser.

Лицензия Firefox — **MPL 2.0**, форк и распространение разрешены. Обязательства:
сохранять MPL на изменённых файлах, публиковать их исходники и **не использовать
товарные знаки Mozilla** — имя Firefox, логотипы, фирменные цвета. Для нас это не
проблема: у нас свой бренд, и весь брендинг Mozilla в сборке заменяется.

## Два трека разработки

Собрать Firefox с нуля — это 40+ ГБ на диске и часы компиляции на каждую итерацию.
Проверять на этом цикле оттенок кнопки невозможно. Поэтому работа идёт двумя
дорожками, и код между ними переносится почти без изменений.

### Трек A — прототип интерфейса (`ui/`)

Тот же CSS, что будет в продукте, но применяется к готовому Firefox через профиль
разработчика. Цикл правки — секунды: `Ctrl+Alt+R` перечитывает стили прямо в
работающем браузере.

```
tools/dev-profile.ps1     создаёт профиль, подключает ui/chrome, запускает
ui/chrome/userChrome.css  точка входа интерфейса
ui/chrome/vantara/*.css   компоненты
ui/prefs/user.js          настройки приватности
```

Здесь отлаживается всё, что можно выразить через CSS и chrome-скрипты: внешний
вид, анимации, поведение вкладок, панели. Это примерно 80% работы над интерфейсом.

**Чего трек A не может:** своего исполняемого файла, своего имени в системе,
изменений в C++, собственного канала обновлений, иконки в трее.

### Трек B — сборка форка (`src/`, `engine/`)

Настоящий продукт: `vantara.exe` со своим брендом, установщиком и обновлениями.

```
engine/     исходники Firefox — скачиваются, в git не хранятся (~30 ГБ)
src/        наш оверлей: файлы, которые кладутся поверх engine/
patches/    патчи к файлам Firefox, которые нельзя просто заменить
```

Сборкой управляет **surfer** — инструмент, написанный командой Zen Browser
именно для форков Firefox. Он скачивает исходники нужной версии, накладывает
`src/` и патчи, подставляет брендинг и собирает установщик.

Ключевое свойство: обновление до новой версии Firefox — это `surfer update`,
а не ручной перенос изменений. Патчи применяются заново, конфликты видно сразу.
Без такого инструмента форк отстаёт от Firefox по безопасности, а это для
браузера с упором на защиту данных недопустимо.

## Слои изменения интерфейса

От дешёвого к дорогому. Каждый следующий слой нужен, только если предыдущего
не хватило.

| Слой | Что можно | Цена | Где живёт |
|---|---|---|---|
| **1. CSS** | Полное переоформление: цвета, форма, размеры, анимации, скрытие элементов | Дёшево, мгновенная итерация | `ui/chrome/` → `src/browser/themes/vantara/` |
| **2. Chrome-скрипты** | Новые кнопки и панели, своя логика вкладок, реакция на события движка | Средне, нужен перезапуск окна | `src/browser/base/content/vantara/` |
| **3. Своя разметка окна** | Другая структура браузера: вертикальные вкладки, свои зоны интерфейса | Дорого, ломается при обновлении Firefox | патч `browser.xhtml` |
| **4. Патчи C++** | Поведение сети, хранилища, защиты от отпечатка — то, что недоступно из JS | Очень дорого, требует ревью на каждое обновление | `patches/` |

«Кастомный интерфейс, а не базовый» достигается слоями 1–3. Слой 4 нужен только
для приватности — например, чтобы срезать данные до того, как они попадут в сеть,
а не после.

## Структура репозитория

```
Vantara/
├─ brand/              логотипы и иконки всех размеров
│  ├─ source/          исходный брендшит
│  ├─ logo/            нарезанные элементы
│  ├─ icons/           набор иконок приложения + .ico
│  └─ tray/            иконка трея
├─ docs/               документация проекта
├─ ui/                 трек A: прототип интерфейса
│  ├─ chrome/          CSS интерфейса
│  └─ prefs/           настройки приватности
├─ src/                трек B: оверлей поверх исходников Firefox
├─ tools/              скрипты сборки и разработки
├─ .dev-profile/       профиль разработчика (не в git)
├─ .dev-runtime/       portable-движок для отладки (не в git)
└─ engine/             исходники Firefox (не в git)
```

## Порядок работ

Трек A запускается сразу и идёт постоянно. Трек B подключается, когда интерфейс
устоялся настолько, что его имеет смысл вкомпилировать. Разделение снимает
главный риск таких проектов: месяцы возни со сборкой до того, как появится
что-то, на что можно посмотреть.

Этапы — в [ROADMAP.md](ROADMAP.md). Порядок сборки форка — в [BUILD.md](BUILD.md).
